> 本文档是给其他 AI / 协作者执行的权威实施计划。基于 2026-08-25 全项目占位功能排查。
> 执行顺序按"收益最大、影响面最广"排序。每项含：现状、目标、涉及文件、具体改动、验证方法。

### 数据模型关键事实（schema.prisma）

- **PracticeHistory**（表 `practice_history`）：`id / questionId / status / durationSeconds / attemptedAt / userId?`。`userId` 可空，索引 `[userId, attemptedAt]`。
- **TestCase**（表 `test_cases`）：`id / questionId / input / output / isHidden / orderBy`。
- **Notification**（表 `notifications`）：`id / userId / type / title / body? / link? / read / createdAt`。type 枚举注释：`"follow" | "comment_reply" | "mention" | "reminder" | "system"`。
- **Follow**（表 `follows`）：`id / followerId / followingId / createdAt`，唯一约束 `[followerId, followingId]`。

### 代码执行（src/lib/code-runner.ts）

- `runCode(sourceCode, language, stdin?)` 真接 Piston API。语言：javascript/typescript/python/java/cpp。
- 普通题目判题用 `wrapCode()` 注入 I/O + 逐个 TestCase 比对（`questions/[id]/submit/route.ts`）。

### 鉴权模式（src/lib/session.ts）

- API 保护用 `requireAuth()` 返回 401 或 null，然后 `auth()`/`getCurrentUser()` 拿 session。
- 前端受保护页用 `AuthGuard` 包裹。

## 1. 【🔴】练习统计链路修复（最高优先，盘活排行榜/签到/每日一题）

### 现状
- `src/app/api/questions/[id]/submit/route.ts` 第 283-285 行**注释掉了** PracticeHistory 写入（单用户遗留）。
- 前端无任何组件调用 `POST /api/practice`。
- 连锁影响：`leaderboard`、`stats/*`、`streak`、`daily-question`、`reminders` 依赖 `practice_history` 表 → 实际基本为空。

### 目标
做题提交后自动写 PracticeHistory，多用户化；恢复排行榜/统计/签到数据。

### 改动步骤

**1.1 恢复 `questions/[id]/submit/route.ts` 写入 PracticeHistory**
- 文件：`src/app/api/questions/[id]/submit/route.ts`
- 该路由当前**未鉴权**（第 177 行 POST 无 requireAuth）。需要：
  - 引入 `import { auth } from "@/lib/auth"`。
  - POST 内 `const session = await auth()`，`const userId = session?.user?.id ?? null`（未登录不阻塞判题，但 userId 为 null 则不写记录，或干脆要求登录——需与产品确认）。
- 在第 281 行 `passedCount` 之后、return 之前，追加：
  ```ts
  if (userId) {
    await prisma.practiceHistory.create({
      data: {
        questionId,
        userId,
        status: overallStatus, // "accepted" | "wrong_answer" | ...
        durationSeconds: Math.round(totalDuration / 1000),
      },
    });
  }
  ```
- 注意：失败多次会重复插入多条记录。若需"每题最近一次"语义，可先 `deleteMany({ questionId, userId })` 再 create，或保留多条（groupBy 按 questionId 取最新，reminders 已用该逻辑，保留多条可行）。

**1.2 确认 `/api/practice` POST 已多用户化**
- 文件：`src/app/api/practice/route.ts`。检查是否用 `userId: null` 硬编码，若有改为当前用户（参照已改好的 `reminders/route.ts`）。

**1.3 检查下游消费方**
- `leaderboard/route.ts`、`stats/*/route.ts`、`streak/route.ts`、`daily-question/route.ts`：确认它们都用 `userId` 过滤，而非 `userId: null`。有硬编码 `null` 的地方改多用户。

### 验证
- 登录后提交一道题（有 TestCase 的），查 `practice_history` 表出现记录。
- 排行榜/统计页出现该用户数据。

## 2. 【🔴】竞赛评测改为真实 TestCase 判题

### 现状
- `src/app/api/contests/[id]/submit/route.ts` 第 65 行 `runCode(code, language)` **没传测试用例**。
- 判定只看 `result.code !== 0`，能运行即 `accepted` 满分。不用 `TestCase`。

### 目标
复用 `questions/[id]/submit/route.ts` 的 `wrapCode()` + TestCase 逐用例判题逻辑。

### 改动步骤

**2.1 抽取公共判题函数**
- 新建 `src/lib/judge.ts`，把 `questions/[id]/submit/route.ts` 的 `wrapCode`（4 语言）+ 逐 TestCase 执行 + 状态判定逻辑提取为：
  ```ts
  export interface JudgeResult { status; passedCount; totalCount; duration; results; }
  export async function judgeCode(questionId, code, language): Promise<JudgeResult>
  ```
  其中读取该题的可见 TestCase（`isHidden: false`）、逐个 `runCode(wrappedCode, language, tc.input)`、比对 output、判定 `accepted/wrong_answer/runtime_error/time_limit_exceeded`。
- `questions/[id]/submit/route.ts` 改为调用 `judgeCode`（保持对外行为不变）。

**2.2 竞赛评测调用 judgeCode**
- `contests/[id]/submit/route.ts` 改为 `judgeCode(questionId, code, language)`，用返回的 `status/passedCount/totalCount` 计算得分。
- 竞赛得分策略（需产品确认）：全部通过得 `contest.problems[0].score`；部分通过可按 `passedCount/totalCount * score` 折算，或全对才得分。默认建议"全对才得分，部分通过记 status=partial 分 0 或按比例"。

### 验证
- 创建带 TestCase 的竞赛题，提交错误代码 → `wrong_answer`；提交正确代码 → `accepted`。

## 3. 【🔴】通知产生逻辑

### 现状
- `prisma.notification.create` 只在 `notifications/route.ts` 的 POST（用户自己造通知）出现。
- **无任何业务事件**自动创建通知 → 用户永远不会收到通知。

### 目标
在关键业务动作发生时自动给目标用户创建通知。

### 改动步骤

**3.1 新建通知工具函数**
- 新建 `src/lib/notify.ts`：
  ```ts
  export async function createNotification(input: {
    userId: string;
    type: "follow" | "comment_reply" | "mention" | "reminder" | "system";
    title: string;
    body?: string;
    link?: string;
  }) {
    await prisma.notification.create({ data: input });
  }
  ```
- 需忽略"自己给自己通知"（发通知者 ≠ 接收者时才算）。

**3.2 在业务动作处接入（按现有 API 找触发点）**
- **评论被回复**：`src/app/api/comments/*`（创建评论时，若是对已有评论的回复，通知原评论作者，type=comment_reply，link=题目页）。
- **题解被点赞**：`solutions/*` 的 upvote 逻辑，通知题解作者。
- **新评论**：通知题目作者（若题主存在）。
- **关注**：在功能 4 的 follow API 中接入（type=follow，link=关注者主页）。
- 每个触发点：先查目标用户 id，`if (targetUserId && targetUserId !== actorId)` 才 `createNotification`。

### 验证
- 用户 A 回复用户 B 的评论 → B 的通知列表出现新通知。

## 4. 【🟡】关注（Follow）功能

### 现状
- schema 已有 `Follow` 模型，后端无 API，前端无按钮。

### 改动步骤

**4.1 后端 API**：新建 `src/app/api/follow/route.ts`
- `POST { followingId }`：`requireAuth()` → `prisma.follow.create({ data: { followerId, followingId } })`，处理唯一冲突（upsert 或 catch P2002）。禁止关注自己。可顺便 `createNotification(type=follow)`。
- `DELETE ?followingId=xxx`：取消关注。
- `GET ?userId=xxx`：查某用户的关注/粉丝列表（或分开 `/api/users/[id]/followers`）。

**4.2 前端**：用户主页 `src/app/profile/page.tsx` 与 `src/app/users/[id]/page.tsx`（若有）
- 加"关注/取消关注"按钮（仅登录用户、且非本人时显示）。
- 显示关注数/粉丝数。

### 验证
- 登录 A 关注 B → B 主页粉丝数 +1，A 主页关注数 +1；B 收到 follow 通知。

## 通用验证流程（每项完成后必做）

1. `npx tsc --noEmit` → 0 错误
2. `pnpm lint` → 0 error（现有 warning 可忽略，如 Tailwind 类名风格）
3. 改 schema 后：`npx prisma migrate dev --name <desc>`（遇 drift 则手写 migration + `npx prisma migrate deploy` + `npx prisma generate`）
4. 重启 dev（`pnpm dev:https`，端口 3001），浏览器冒烟测试
5. 涉及数据库的操作，可用临时测试账号（如 `test-prefs@interview.com`）验证后清理

## 关键约定

- 所有新 API 用 `requireAuth()` 鉴权（`src/lib/session.ts`）。
- 多用户化：禁止硬编码 `userId: null`（这是单用户遗留）。统一用 `session.user.id`。
- 代码风格遵循项目现有模式（Prisma 单例 `src/lib/prisma.ts`、API 返回 NextResponse.json、错误处理 try/catch）。
- 不要手改既有迁移文件；新增字段用新迁移。
